action="create_gadget", name=<new kebab-case name>, reason=<why you need it>, description=<one line>, dependencies=[<npm packages>], source=<TypeScript>
  Write a gadget you do not have yet.
  The user reads the whole file and decides, so reason is required and must be honest:
  they are about to let code run on their machine. If they say no you are told why, so
  change the gadget and ask again rather than repeating the call.
  source must be a complete TypeScript file that starts with this exact 4-line comment
  header, where the words `name:` and `description:` are literal and required:

  /**
   * name: count-lines
   * description: counts the lines of a file. input: { path: string }
   */

  Then code that compiles with bun, ending in:
  export default async (input: { path: string }) => string
  `node:*` builtins and the `Bun` global are always there, as are `react` and `react-dom`.
  Any other package has to be asked for by name in `dependencies`, as `name@range`:
  import { z } from "zod" means dependencies=["zod@^4"]. A gadget that imports a package it
  did not ask for is refused, so list every one of them and nothing else. They are installed
  into the home with a `bun.lock`, which is what makes a gadget written today run the same
  code tomorrow. Deleting the last gadget here that imports a package takes it out again, so
  a home does not accumulate them.
  The description is all you will see about this gadget later, so name its input fields.
  A gadget may take a second argument, `ui`, to put an interface in front of the user. That
  has a language of its own: call action="load_ui" for it, and add the line `* ui: true` to
  the header. Without a UI to draw on such a gadget cannot run, and is not listed either.
  A gadget may take a third argument, `state`, with `state.session` and `state.persistent`.
  Both offer `await state.X.get(key)` and `await state.X.set(key, value)`, and both are shared
  by every gadget in the run, so one can leave something for the next to pick up. `session`
  holds any value and is gone when the conversation is cleared; `persistent` is committed to
  the home and is still there in a later session, so it only holds json: an object, array,
  number, string, boolean or null.
action="test_gadget", reason=<why you need it>, description=<one line>, source=<TypeScript>, input=<object>
  Run a gadget you wrote without committing it. Same file, same header, same rules and same
  approval as create_gadget, but nothing is written to the home and it does not outlive the
  call, so use it to get the source right and then commit exactly what you tested. State is the
  exception: a gadget that commits during a test really has committed it.
  A test needs no `dependencies`. It runs out of a temp folder that belongs to no home, so
  whatever the source imports is installed there and the home is never touched either way.
  That also means a test imports `latest` where the committed gadget imports the locked version,
  so a test that passes is not a promise the commit behaves identically.
  A gadget whose component imports a package cannot be drawn in a test, because the window only
  draws what the home has installed. Commit it first.
action="load_gadget", name=<existing gadget>
  Read a gadget's whole source back. All you have of a gadget is its description, so this
  is how you see what one you wrote earlier actually does when it misbehaves: read it,
  change it, and commit the whole file again with create_gadget under the same name, which
  takes effect the next time it runs.
action="create_protocol", name=<kebab-case name>, when=<when to load it>, description=<one line>, content=<knowledge>
  Save knowledge worth keeping. Never save a guess: only what you actually learned.
  A name that already exists is replaced rather than refused, so this is also how you
  correct memory you have come to doubt: call action="load_protocol" first if you want
  to see what you are replacing. The user reads it before it is committed, to check the
  memory is right rather than the prose, so there is no reason to give.
action="delete_gadget", name=<existing gadget>, reason=<why it should go>
  Throw a gadget away for good. There is no undo and nothing reads it again, so reason is
  required and must be honest about what is wrong with it. The user reads the whole file
  before deciding, because that file is the only version of it there will ever be.
action="delete_protocol", name=<existing protocol>, reason=<why it should go>
  Throw a protocol away for good, which is how you correct memory you got wrong. reason is
  required for the same reason. The user reads the body before deciding.
action="load_ui"
  The language for a gadget's `ui` argument. You cannot guess it: call this before writing
  a gadget that takes a second argument.
